# M37 moving Create Funnels across the Sable boundary

Target bytecode: Create 6.0.8, commit `1a1a9a2819b4f89f78caec41b55ed8cb222fa24b`.
This milestone changes only the moving `FunnelMovementBehaviour` for Andesite and Brass Funnels inside a Sable-hosted native Create contraption.

## Exact Create path

`AbstractContraptionEntity.tickActors()` calculates the actor's active point from `MovementBehaviour.getActiveAreaOffset(context)`, applies the inner contraption transform, sets `MovementContext.position`, and invokes `visitNewPosition(context, BlockPos)` when the active cell changes. `FunnelMovementBehaviour.getActiveAreaOffset()` uses `FunnelBlock.getFunnelFacing(context.state)` with a 0.15-block extraction or 0.65-block collection offset (UP always uses 0.65). `visitNewPosition()` selects `extract` when `FunnelBlock.EXTRACTING` is true; otherwise it selects `succ`.

`extract` checks the target block's collision shape and whether its output cell already contains an `ItemEntity`. It applies Create's filter, `FilterAmount` and `UpTo` fields, calls `ItemHelper.extract` on `context.contraption.getStorage().getAllItems()`, and creates an `ItemEntity(context.world, context.position, stack)` with native pickup delay, sound and zero velocity. `succ` calls `Level.getEntities(null, new AABB(pos), ItemEntity-or-PackageEntity predicate)`, applies `context.getFilterFromBE().test`, then calls `ItemHandlerHelper.insertItemStacked` on the same native mounted storage and updates or discards the source entity. The actor has no direct adjacent-inventory capability lookup or block-entity lookup. It does not override `tick`, `renderInContraption`, `createVisual` or `disableBlockEntityRendering`; those are `MovementBehaviour` defaults.

Stationary Funnels are separate: `FunnelBlockEntity.tick()` selects a mode, and `activateExtractor()` uses `InvManipulationBehaviour` and `VersionedInventoryTrackerBehaviour`; `FunnelBlock.entityInside()` uses its native filter and `tryInsert` path. Parent-world inventory transfer therefore requires a stationary parent Funnel or other native Create transport in addition to the moving actor. A Sable-specific direct item copier would change Create 6.0.8 semantics and is not included.

## Coordinate and ownership contract

`FUNNEL_LOCAL` is the actor block in the inner Create contraption. Create's inner transform yields the active point in `SABLE_RAW`; the outer Sable `logicalPose()` maps that point and the rotated actor facing to `PARENT_VISIBLE`. `BlockPos.containing` gives `PARENT_BLOCK`. The one-block entity query uses the same cell in `PARENT_ENTITY_SPACE`.

Only a Sable-contained `FunnelMovementBehaviour` enters the compatibility path. `SableMovingFunnelTarget` reuses the M36 source-backed level/cardinal orientation envelope, checks the parent chunk, rejects hidden-plot storage and another Sable's physical bounds, and returns no target on failure. There is no raw-coordinate fallback. The hook temporarily presents a parent-visible `MovementContext.position` to the original Create method and restores raw fields in `try`-with-resources. Since `context.world` already is the parent `ServerLevel`, the original Create item query and ItemEntity creation now occur in the physical parent world. The server owns mutations; the scoped client path performs no independent item transfer.

Create's ordinary `visitNewPosition` trigger tracks inner raw cell changes. An outer Sable can move while that raw cell remains unchanged, so a Sable-only `tick` compares the physical parent cell with the previous one and invokes the same native `visitNewPosition` when it changes. Native filter, amount, mounted-storage and ItemEntity bookkeeping are not replaced. No item capability or block-entity reference is cached.

M29's general entity getter intentionally also searches overlapping sublevels. The Funnel's exact `succ` and `extract` item queries are therefore narrowed at their own call sites to entities outside every hidden Sable plot. This prevents a physically parent-world pickup from consuming a raw-storage `ItemEntity`, while leaving all unrelated entity queries and ordinary Create Funnels unchanged.

The Funnel has no actor-specific `ActorVisual` or CPU `renderInContraption` implementation. Its normal contraption block/block-entity rendering remains under the established M14/M35 small-coordinate rendering bridge. M37 does not change Flywheel, culling or PoseStack transforms.

## Runtime fixture and chest-render follow-up

The first Minecraft run proved ENTITY pickup: native `succ` raised mounted storage from 0 to 16. INSERT and EXTRACT never ran because setup checked `FunnelBlock.POWERED=true` in the same command chain that placed the adjacent redstone block. Exact Create 6.0.8 `AbstractFunnelBlock.neighborChanged` (`m_6861_`) schedules a one-tick block update; `tick` (`m_213897_`) copies the neighbor signal into `POWERED`. The initial `powered=false` command state is therefore expected at synchronous validation. Setup now checks the redstone signal and block/BE geometry immediately, with component-level diagnostics. Block entities themselves are created through the normal synchronous block-placement path; there is no evidence that a BE delay caused the rollback.

Create's moving chest path is separate from Funnel actor rendering. `ClientContraption.setupRenderLevelAndRenderedBlockEntities` reads captured block info, reconstructs a ChestBlockEntity, adds it to `renderedBlockEntityView`, and sets its render bit. `ContraptionEntityRenderer.render` passes that list and bitset to `BlockEntityRenderHelper.renderBlockEntities`, which checks Flywheel's `skipVanillaRender`, obtains the native ChestRenderer through `BlockEntityRenderDispatcher`, then draws with contraption matrices. The latest runtime confirmed `CHEST_RENDER_DISPATCH` with small camera-relative coordinates, and the chest is visibly moving. That rendering path is frozen.

The second runtime proved moving `extract` and ENTITY `succ`, but not end-to-end INSERT/EXTRACT. Exact Create 6.0.8 moving `extract` creates an ItemEntity at `context.position - (0,0.5,0)` for an UP-facing Funnel, with zero velocity. A subsequent attempted fixture moved the Funnel to `(1,0,-1)`; Create's `RadialChassisBlock.getGlueableSide` maps `sticky_north` to physical UP and `sticky_east` to physical SOUTH for an X-axis chassis, so the north-side Funnel was not natively attached. M37 restores the runtime-proven moving payload: chassis `(1,0,0)`, UP Funnel `(1,1,0)`, chest `(1,0,1)`. The upward parent collector is now `(12,-2,0)`, chest `(12,-3,0)`, beneath the swept payload with a one-block air gap. At the intended active-cell visit, an emitted item's horizontal coordinate is within the collector's X/Z column and it begins at approximately `y=1.65`; it then falls toward Create's native stationary `entityInside` path. Setup prints the actual `getIncludedBlockPositions` result and rejects missing moving blocks before READY. Static drop-column geometry is not a Minecraft transfer PASS.

For EXTRACT, native stationary extraction emits at its block center plus `WEST * 0.25` and `Y + 0.45`; native moving `succ` queries exactly `new AABB(targetBlock)` only when the active cell is visited. Runtime has now proved native stationary spawn precedes native moving `succ` with candidateCount=1 and one successful mounted pickup. The source chest nevertheless lost two items because the stationary Funnel remained enabled during piston travel. On the first observed native spawn, the fixture now places its owned redstone control block, waits for Create's native `POWERED` state and exactly one tagged staged item, and only then releases the native piston clutch. It does not create or remove an item to make the transfer work. EXTRACT acceptance requires exactly one source decrement, one mounted increment, a prior native spawn, and a later native moving query/insert witness; block-target resolution does not apply to an ItemEntity target. A second emission fails this deterministic fixture rather than being reported as PASS.

The fixture summary distinguishes a native moving leg from end-to-end delivery. ENTITY resolves its tagged parent ItemEntity, not a stationary block target; its previously observed 16-item native pickup should therefore report PASS without changing the production actor hook. EXTRACT also requires that stationary spawn preceded the native moving query and a candidate was present. The harness retains its last valid actor position across ordinary native disassembly, so a completed run cannot be relabeled `ACTOR_POSITION_UNAVAILABLE` merely because the CCE has gone away. `INSERT_LAYOUT`, `INSERT_GEOMETRY`, `EXTRACT_GEOMETRY`, and `EXTRACT_TIMING` provide bounded evidence for the next runtime run.

The first M37.2 runtime crashed in the fixture at `logicalPose().transformPosition(actor.getRight().position)`. Create's `MovementContext` constructor initializes `position` to null; `AbstractContraptionEntity.tickActors()` assigns the active point later. The fixture observed the captured actor between those steps. The fixture now treats actor pose and item geometry as optional observations: `WAIT_FOR_MOVING_CONTRAPTION`, `WAIT_FOR_ACTOR_POSITION`, `WAIT_FOR_RELEVANT_ITEM_ENTITY`, then `CAPTURED`. Only a non-null actor position enters the fixture's pose transform. Missing observations print one bounded pending transition; a prolonged missing mandatory actor pose stops the fixture run gracefully. `Pose3dc` and the production actor are unchanged.

Fixture state classification: marker, mode, origin, outer body and native piston controller are mandatory for a live run. `MovementContext.position`, the last visible active point/block and the tracked emitted-item UUID are optional observations. An emitted item's position/AABB and intake/query overlap are derived only after that entity exists. The `cleanup` command removes the in-memory run regardless of geometry phase, then reconstructs ownership from persistent fixture markers and native blocks/entities. This also recovers the assembled INSERT fixture left by the crash after a server restart.

## Topology matrix

| Case | Status | Source-derived reason |
| --- | --- | --- |
| F1 moving Funnel to parent inventory | Supported only through native stationary parent Funnel | Moving `extract` emits an item entity, not a direct capability insertion. |
| F2 parent inventory to moving Funnel | Supported only through native stationary parent Funnel | Moving `succ` collects an item entity into mounted storage; stationary extraction is separate. |
| F3 moving Funnel and parent ItemEntity | Runtime-proven | Original `succ` captured 16 parent items into mounted storage. |
| F4 stationary Funnel on Sable hull to parent inventory | New architecture required | No moving actor context drives its stationary `InvManipulationBehaviour`. |
| F5 Funnel and storage within one Sable-owned inner Create contraption | Already native for mounted storage | `getAllItems()` remains the captured inner contraption's storage. |
| F6 Sable A to Sable B | Safe no-op | Physical target overlapping another Sable is rejected. |
| F7 ordinary non-Sable moving Funnel | Already native | `owner(context) == null` invokes original Create method unchanged. |

The production hook does not implement direct F1/F2 capability transfer. The closest faithful parent-inventory fixture is a composition of two native Create mechanisms: the moving Funnel's ItemEntity path and a stationary Funnel attached to the parent chest.
